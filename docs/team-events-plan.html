Relay and Duo: team events

Design plan. One bib per team on the boards, one tag per runner so every member's finish is proven.

1. The problem

The client's listing has one row per runner (First Name, Last Name, Team Name, Gender, DOB, Category = RELAY / DUO). Our import wants bib, name, gender, age, tag: one row per participant, one bib each, one tag each, and (event, bib) is unique.

  • Teams exist in the system only as a free-text extra column. There is no team, no leg and no member.
  • If every teammate shares one bib and one tag, a single read at the finish looks like "the team finished". We can not tell whether the second runner of a duo, or the third of a relay, ever crossed.
  • The import can not take the client's file as it is (no bib, name split in two columns, team name).

2. Decision

Team = one bib. Member = one tag.
  • The team is the one ranked participant. Its bib is the team bib, its name is the Team Name. Boards, release levels, ranking and override keep working as they do today.
  • Each member is a row under that team with its own RFID tag (or bib sticker) and a leg order. A read of a member's tag resolves to the team bib and remembers who it was.
  • The team is FINISHED only when every member has a finish read after the start (or an admin override). Team finish time = the last member's finish read.
QuestionAnswer
Same bib for duo and relay?Same bib per team, never per runner. The tag is what separates people.
How do we know everyone crossed?The team has N members and needs N distinct member finish reads. The board shows progress such as 1/2 until complete.
What if a chip fails to read?The team stays "in progress, incomplete". An admin reconciles it with the existing override (reason + proof photo).
Live board vs final board?Live: Team Name only, then FINISHED. Final (after reconcile): names and every split.

5. Diagram C: finish rule for a duo

If B never reads: admin sets the finish override on the team (reason + proof photo, existing flow). Reads are never deleted.

Relay legs. The rule is the same: N members, N finish reads. The leg order is stored for display (who ran leg 1, 2, 3...). Per-leg times are only shown if exchange checkpoints exist; otherwise the final shows each member's finish read.

The old bib, name, gender, age, tag file keeps working unchanged. The importer decides by the presence of a Team Name column plus a team category.

Import checks: duplicate tag anywhere in the event is rejected; a team with the wrong number of members is flagged (not blocked); re-importing the same file updates members instead of creating duplicates.

8. Edge cases

CaseBehaviour
Member chip does not read at finishTeam stays incomplete 1/2. Marshal can type the member's tag/bib manually; otherwise admin override.
Same member read twice at finishCounts once (distinct members). First read after start is used, as for solo.
Member read before the startIgnored for finish, same as the existing "reads never hidden by a later start" rule.
Tag given to two peopleBlocked at import and when editing a member.
Team missing a member at importWarning. Team size can be edited; the finish rule uses the actual member count.
Substitute runner on race dayAdmin replaces a member's tag/name; old reads stay attached to the old member.
Duo where one runner is only counted at the finishBoth must cross; team time = last. Gaps between the two are shown in the admin expand row.

9. Build order

  1. Migration team_members plus reads.member_id.
  2. Importer: parse client headers, group by team, auto bibs, validations, tests.
  3. MATCH / live loader: resolve member tag to team bib and member.
  4. computeResults: all-members finish rule, member split data, tests.
  5. Boards: team name only while in progress, names and splits in final, admin expand row.
  6. Station app: carry member tags in the runner sync.
  7. E2E: simulate a duo and a relay through the existing harness.
